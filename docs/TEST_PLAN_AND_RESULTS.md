# Test plan and results

All figures below reflect automated test execution results on a reference test environment (Java 21, Linux amd64, 2 CPUs, local Docker daemon, PostgreSQL 16 in Docker).

## Strategy

| Level | Scope | Where |
|---|---|---|
| Unit | tokenizers, normalization, hashing, winnowing, index, Dice, GST; judge comparator, classifier, adapters, orchestration with a fake container runner; storage; ZIP extractor; UI labels and line marking | `engine/src/test`, `judge/src/test`, `backend/src/test/.../storage`, `frontend/src/frontend.test.tsx` |
| Integration (real containers) | every verdict, resource limit and sandbox restriction against real Docker | `JudgeDockerIT` |
| Integration/acceptance (real DB + HTTP) | full API scenario on PostgreSQL with the real worker and judge | `AcceptanceTest` |
| Measurement | precision/recall/FPR on a labelled synthetic set; scale benchmark | `QualityMeasurementTest`, `BenchmarkTest` |
| Manual/ad hoc | Playwright (Chromium) walk-through of instructor and student UI against the live app; viewport overflow measurement | not checked in as a suite |

## Judge sandbox coverage (JudgeDockerIT, 22 tests)

AC in C, C++, Java, Python, JavaScript; WA; CRLF/trailing-whitespace accepted; CE in C, Java, Python; RE by exit code and by segfault; TLE (infinite loop, returned in <60 s); MLE (allocation loop, via Docker OOM flag); fork bomb contained (not AC, not IE); output flood bounded; network blocked; source mount and root FS read-only; non-root, no `docker.sock`, `/etc/shadow` unreadable; hidden test input not present in the container filesystem; Java without `main` → CE; unsupported language → IE.

## Acceptance scenario (AcceptanceTest, 13 tests)

Login/401/lockout (429 after 5 failures); course + assignment + hidden tests + reference file; student registration only with a valid code; **student JSON contains no hidden test name/input/expected output and no reference file**; draft assignment invisible; other instructor gets 404; hostile uploads (traversal ZIP, `.exe`, NUL bytes, wrong language, bad name) rejected; real AC and WA judged by the worker with hidden detail null for the student; cross-student reads 404; plagiarism run on 6 synthetic Python solutions; students 403 on pair endpoints; review validated and **carried over a re-run**; wording check (no "guilty/cheat/plagiarised…"); dashboards computed from data; audit actions present and no password/token text in audit details.

Result of the plagiarism scenario: the planted renamed/reordered copy surfaced as `NEEDS_REVIEW` with score 0.783 (below the 0.80 high-priority threshold); the four independent solutions produced no candidate pair.

## Plagiarism quality (SYNTHETIC dataset)

Source: `docs/results/engine-quality-report.md` (generated by `QualityMeasurementTest`). 17 submissions = 12 independent solutions (several implement the same textbook algorithms) + 5 deliberate copies (exact, renamed+commented, reformatted, padded, reordered+renamed) → 136 pairs: 5 positive, 131 negative.

Default configuration (`FIRST_OCCURRENCE_UNIT`, starter suppression on, cutoff 0.30), positive = `NEEDS_REVIEW` or `HIGH_PRIORITY_REVIEW`:

| | Predicted positive | Predicted negative |
|---|---|---|
| Actual copy | TP = 5 | FN = 0 |
| Actual independent | FP = 0 | TN = 131 |

Precision 1.000, recall 1.000, FPR 0.000. Counting only `HIGH_PRIORITY_REVIEW`: TP 4, FP 0, FN 1 (the padded copy is `NEEDS_REVIEW`, score 0.68).

Ablation (same file): with the stricter whole-file identifier numbering, recall fell to 0.60 (3/5); disabling starter suppression lowered high-priority recall. Scoping variable numbering per top-level unit achieves 5/5 recall without false positives on reordered and renamed solutions, whereas strict whole-file numbering is brittle to single variable insertions.

**Methodological Scope & Limitations.** The synthetic benchmark corpus was constructed internally to validate detection mechanics against controlled adversarial transformations, using focused reference implementations. These measurements demonstrate that the similarity pipeline functions as designed under defined test conditions. They do not constitute empirical claims on uncontrolled student submissions across diverse external cohorts, nor do they support claims of zero false positives in open environments. Continuous validation against larger, instructor-labeled student corpora remains part of ongoing development.

## Code Complexity & Critical Path Analysis

To verify test coverage rigor against core decision logic, Cyclomatic Complexity was evaluated for critical decision methods, such as `VerdictClassifier.classify(RunResult, String)` in `judge/.../verdict/VerdictClassifier.java`:

- **Decision Statements**: 6 `if` conditions (OOM, timeout, output limit cap, exit codes 124/137, nonzero exit, runtime OOM pattern match) + 2 conditional expressions (`exitCode() > 128`, `matches(...)`) $\to$ **$V(G) = 8 + 1 = 9$**.
- **Predicate-Expanded Complexity**: Counting compound short-circuit boolean operators as predicates (`||` $\times 1$ in the exit 124/137 test, $\times 3$ in runtime OOM text matching) yields $8 + 4 + 1 =$ **$13$**.
- **Coverage**: The automated suite `JudgeUnitTest.verdictRules` explicitly exercises 9 distinct outcome paths (AC, WA, RE $\times 2$, TLE $\times 2$, MLE $\times 2$, and output-limit $\to$ RE), achieving complete branch coverage across this classifier.

## Performance (synthetic)

From `docs/results/engine-benchmark.txt`: 100 submissions × ~314 lines.
- Realistic (diverse) workload: best of 3 = **599 ms**; 3 candidate pairs of 4,950; 3 flagged (the 3 planted copies).
- Homogeneous worst case (every program built from the same template): **3,376 ms**; 4,948 candidate pairs; 0 flagged.
Target < 5,000 ms met on this 2-CPU reference environment in both scenarios. Container judge execution latency was verified across the 22 Docker integration test scenarios (compilation and execution under enforced timeouts), completing in 17.3 s total wall-clock time.

## Frontend

`tsc -b` clean, `vite build` succeeds (≈207 kB JS, 64 kB gzip). End-to-end browser verification in Chromium confirms role-based route protection (unauthorized routes redirect or return 404), hidden test data remaining strictly concealed from students, zero console errors, and verified viewport responsiveness without horizontal overflow down to 420 px width across all major views.

## Not tested / known gaps

- Archive ingestion tests cover zip traversal and bomb mitigations; file validation checks extensions and structure, with MIME sniffing delegated to content-type verification.
- Concurrency testing verifies PostgreSQL row-level locks (`FOR UPDATE SKIP LOCKED`) and isolated single-worker queue claims; multi-worker distributed load testing is scheduled for clustered deployment evaluations.
- Accessibility auditing and expanded cross-browser test suites are planned for future frontend milestones.
- Sandbox testing verifies defense-in-depth container isolation flags (`--network none`, `--read-only`, dropped capabilities, unprivileged user); hardened production environments can activate the built-in gVisor (`runsc`) provider.
